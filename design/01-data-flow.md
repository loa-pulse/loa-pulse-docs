# 01. 데이터 흐름과 이벤트

> 모듈 사이를 데이터가 지나갈 때의 실행 방식을 정한다. 모듈 안의 흐름은 [modules/](modules/)를 따른다.

## 시세 갱신 흐름

```
[수집 스레드]
collector ── MarketDataSink.save() ──▶ market: 트랜잭션 안에서 저장
                                         └─ PriceUpdated 발행 (커밋 후 전달)
                                              │
                         ┌────────────────────┴────────────────────┐
                         ▼ [alert 스레드 풀]                        ▼ [realtime 스레드 풀]
                   alert: 조건 매칭, 상태 전이              realtime: SSE 전송
```

## 이벤트 처리 시점: 커밋 후

`PriceUpdated`는 market의 저장 트랜잭션이 **커밋된 뒤에** 전달한다 (`@TransactionalEventListener(phase = AFTER_COMMIT)`).

커밋 전에 처리하면 생기는 문제:
- 저장이 롤백됐는데 브라우저에는 이미 새 가격이 나가 있다.
- alert가 커밋되지 않은 시세를 기준으로 알림을 보낸다.

## 이벤트 처리 스레드: 모듈별 비동기 스레드 풀

[D13](decisions.md#d13-priceupdated는-모듈별-비동기-스레드-풀에서-처리하고-대기열이-차면-버린다)

- 수집 스레드는 저장까지만 하고 바로 다음 수집으로 넘어간다.
- alert와 realtime은 **각자 별도의 스레드 풀**에서 이벤트를 처리한다. SSE 전송이 밀려도 알림 처리는 영향을 받지 않는다.
- 스레드 풀의 대기열은 크기를 제한한다. **대기열이 가득 차면 새 이벤트를 버린다.**
- 버린 이벤트 수는 지표로 남기고 상태 페이지(F12)에 보여준다.

## 알림 발송 흐름: 발송 워커 (아웃박스)

[D14](decisions.md#d14-알림-발송은-워커가-처리하고-최소-1번-발송을-보장한다)

```
[alert 스레드 풀]  상태 전이 + Notification(PENDING) 생성  ← 한 트랜잭션. 여기서 끝
                                   │ (DB에 기록됨)
                                   ▼
[발송 워커, 몇 초마다]
  1. 선점    PENDING이고 재시도 시각이 지난 건을 가져가며 "선점 만료 시각"을 기록
             SELECT ... FOR UPDATE SKIP LOCKED  (짧은 트랜잭션)
  2. 발송    트랜잭션 밖에서 디스코드 DM 또는 웹 토스트 발송
  3. 기록    성공 → SENT / 실패 → 원인에 따라 즉시 FAILED 또는 다음 재시도 시각 설정 (D21)
```

- **발송 경로는 워커 하나뿐이다.** 재시도, 서버 재시작 후 복구, 디스코드 호출 제한 조절을 모두 이곳에서 처리한다.
- **여러 인스턴스(M4)**: 인스턴스마다 워커가 돌아도 `SKIP LOCKED`로 같은 행을 동시에 가져가지 않는다. 리더 선출이 필요 없다.
- **선점 만료**: 워커가 2번이나 3번 도중에 죽으면, 선점 만료 시각이 지난 뒤 다른 워커가 다시 가져간다.
- **재시도**: 사용자 쪽 원인(서버 이탈, DM 수신 거부)이면 즉시 `FAILED`. 일시 장애(5xx, 타임아웃, 429)면 간격을 늘려가며(예: 10초 → 1분 → 5분 → 5분...) 재시도하고, 알림 생성 후 1시간이 지나면 `FAILED`. 자세한 내용은 [03-operations.md](03-operations.md)와 D21을 따른다.
- **디스코드 호출 제한**: 디스코드가 제한 응답(429)을 주면 응답에 담긴 대기 시간만큼 기다린다. 급변동 알림처럼 한 번에 많은 DM을 보낼 때 특히 중요하다.
- **웹 채널**: 접속 중이면 realtime으로 토스트를 보내고, 접속 중이 아니면 보내지 않고 `SENT`로 기록한다 (알림 내역에만 남는다). 재시도하지 않는다.

### 전달 보장: 최소 1번

디스코드 DM API에는 멱등 키가 없어서 정확히 1번 발송은 불가능하다. **누락보다 중복이 낫다고 판단해 최소 1번을 택한다.**

| 장애 시점 | 결과 |
|---|---|
| 발송 전에 워커가 죽음 | 선점 만료 후 다시 발송 → 정상적으로 1번 받음 |
| 발송 성공 후, SENT 기록 전에 워커가 죽음 | 선점 만료 후 다시 발송 → **같은 DM을 2번 받음** |

중복이 생기는 구간은 "발송 성공"과 "SENT 기록" 사이로 최소화한다.

## 브라우저 실시간 전달 (SSE)

[D15](decisions.md#d15-마지막-갱신-시각은-10초-주기-freshness-이벤트로-전달한다)

### 연결

- 브라우저 하나당 연결 하나: `/api/stream?items=1,2,3&ranking=true`
- 구독할 대상은 쿼리로 지정한다. 페이지를 옮기면 다시 연결한다 (D4).
- 로그인 상태면 세션 쿠키로 사용자를 식별해서, 본인 알림도 같은 연결로 보낸다.

### 이벤트 종류

| 이벤트 | 내용 | 언제 |
|---|---|---|
| `price` | 아이템 ID, 현재가, 직전 가격, 1시간 변동률, 수집 시각 | 구독한 아이템의 가격이 바뀌었을 때 |
| `ranking` | 상승·하락 TOP 10 | 랭킹을 구독했고 결과가 바뀌었을 때 |
| `freshness` | 구독한 아이템별 마지막 갱신 시각, 서비스 상태(정상 / 수집 지연 / 게임 점검) | 10초마다 |
| `notification` | 본인 알림 토스트 내용 | 로그인 사용자에게 웹 알림이 생겼을 때 |

- `freshness`는 realtime이 market의 `LatestPriceQuery`(갱신 시각)와 collector의 `CollectionStatusQuery`(서비스 상태)로 조회해서 보낸다. 수집 이벤트와 분리돼 있어서 D11(가격이 바뀐 아이템만 발행)을 그대로 유지한다.
- `freshness`는 **연결 유지 신호(heartbeat)**도 겸한다. 프록시나 Ingress가 데이터 없는 연결을 끊지 않게 한다.
- `freshness`의 서비스 상태로 [기획 4.1](../planning/04-policies.md)의 상단 배너를 띄운다.

### 연결과 재연결

연결하거나 재연결하면, 구독한 대상의 최신 `price`, `ranking`, `freshness`를 한 번씩 먼저 보낸다. 놓친 이벤트는 다시 보내지 않는다 ([기획 4.6](../planning/04-policies.md)).
