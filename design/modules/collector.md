# collector 모듈

> 핵심 도메인 · DDD 전술 설계를 충실하게 적용한다

collector가 답하는 질문은 하나다.

> **"분당 100회로, 지금 무엇을 가져와야 사용자가 보는 시세가 가장 신선할까?"**

## 구성 요소

| 구성 요소 | 종류 | 설명 |
|---|---|---|
| `CollectionTarget` | 애그리거트 | 수집 단위 하나와 그 상태 (등급, 마지막 수집 시각, 다음 예정 시각, 연속 실패 횟수, 페이지에 든 아이템 `Id` 목록) |
| `Tier` | 값 객체 | HOT, NORMAL, COLD와 각각의 반영 목표. [기획 4.1](../../planning/04-policies.md)의 반영 목표 |
| `SourceRefreshCycle` | 값 객체 | 원본 갱신 주기와 마지막 갱신 추정 시각. 다음 갱신 예상 시각을 계산한다 (D27) |
| `RefreshCycleEstimator` | 도메인 서비스 | 값이 바뀐 것을 관측한 시각들로 `SourceRefreshCycle`을 추정한다 (D27) |
| `TierPolicy` | 도메인 서비스 | 수요 신호와 변동률을 보고 등급을 정한다 |
| `CallBudget` | 값 객체 | 이번 분에 쓸 수 있는 호출 수. 재시도용 여유분을 따로 떼어 둔다 |
| `CollectionPlanner` | 도메인 서비스 | 예산 안에서 이번에 수집할 대상을 고른다 |

## 수집 단위

로스트아크 API는 카테고리 검색 한 번에 10개 아이템의 시세를 돌려준다 ([07-api-findings.md](../../planning/07-api-findings.md)).
그래서 `CollectionTarget`은 아이템이 아니라 **카테고리 검색 페이지 하나**다 (D26).

- 수집 범위는 거래소에서 아바타를 뺀 모든 카테고리다. 약 650개, 한 바퀴 71회 호출이다.
- 페이지 구성이 정렬에 따라 바뀌지 않도록 **등급순 정렬**로 가져온다.
- 수집할 때마다 페이지에 든 아이템 `Id` 목록을 이전과 비교한다. 달라지면 그 카테고리의 페이지 목록을 다시 만든다.
- 수집 단위 하나에 아이템이 여러 개 들어 있으면, 그중 **가장 높은 등급**을 그 단위의 등급으로 삼는다.

## 원본 갱신 시점 추적

원본 시세는 매 순간 바뀌지 않고 몇 분 간격으로 여러 아이템이 한꺼번에 바뀐다. 갱신 사이에 호출하면 같은 값을 다시 받을 뿐이다 (D27).

- **관측**: 수집 결과의 값이 직전과 다르면 "원본이 바뀌었다"는 관측 하나를 남긴다. 관측 시각은 직전 수집 시각과 이번 수집 시각 사이의 어딘가다.
- **추정**: `RefreshCycleEstimator`가 관측들로 갱신 주기와 마지막 갱신 시각을 추정한다.
- **활용**: 다음 갱신 예상 시각 직후에 한 바퀴를 몰아서 호출한다. 갱신 사이에는 HOT 단위 몇 개로 변화 감지만 한다.
- **추정이 틀릴 때**: 예상 시각에 값이 바뀌지 않으면 짧은 간격으로 변화 감지를 계속하고, 감지되면 그 시각부터 다시 추정한다. 추정이 불안정한 동안에는 고정 주기로 돈다.

## 수집 실행 흐름

수집 실행은 몇 초마다 돈다. 한 번의 실행은 다음과 같다.

```
1. CallBudget 확인        → 이번 분에 남은 호출 수 (재시도용 여유분 제외)
2. CollectionPlanner      → 원본 갱신 직후라면 한 바퀴를, 아니면 변화 감지용 대상을 고른다.
                            예정 시각이 지난 대상들을 지연 비율 순으로 정렬하고, 예산만큼 선택
3. API 호출               → LostArkMarketClient
4. 저장                   → MarketDataSink (D8)
5. 결과 반영              → 성공: 마지막 수집 시각 갱신, 다음 예정 시각 = 다음 원본 갱신 예상 시각
                                  값이 바뀌었으면 RefreshCycleEstimator에 관측 전달
                            실패: 연속 실패 횟수 +1, 짧게 뒤로 미뤄 재시도
```

### 우선순위: 지연 비율

```
지연 비율 = (지금 - 다음 예정 시각) ÷ 등급의 반영 목표
```

| 예시 | 반영 목표 (가안) | 늦은 시간 | 지연 비율 |
|---|---|---|---|
| 파괴석 (HOT) | 30초 | 15초 | 0.5 |
| 각인서A (NORMAL) | 2분 | 48초 | 0.4 |
| 생활재료B (COLD) | 10분 | 1분 | 0.1 |

늦은 시간이 아니라 비율로 비교하는 이유: 시간으로만 비교하면 목표가 긴 COLD 대상이 항상 먼저 뽑혀서 HOT의 신선도가 떨어진다. 비율로 보면 각 등급의 약속(기획 4.1)을 얼마나 어기고 있는지를 공정하게 비교할 수 있다.

실제 운영 범위는 한 바퀴가 한도 안에 들어와서, 지연 비율은 주로 한도가 부족할 때(장애 후 밀린 호출, 시뮬레이터의 아이템 1만 개 실험) 순서를 정한다.

## 등급 결정 규칙 (TierPolicy)

1분마다 전체 대상의 등급을 다시 계산한다.

| 등급 | 조건 (가안, M0 이후 조정) |
|---|---|
| HOT | 활성 알림이 1개 이상 **또는** 관심 등록 3명 이상 **또는** 최근 1시간 변동률 ±5% 이상 |
| COLD | 최근 하루 거래량이 기준 이하 |
| NORMAL | 나머지 |

- 수요 신호(활성 알림 수, 관심 수)는 `DemandSignalPort`로 조회한다 (D5).
- 변동률은 `PriceVolatilityPort`로 market에서 조회한다.

## 일별 통계 수집

로스트아크 API의 일별 통계(평균가, 거래량)는 아이템마다 하루 1번 가져온다 ([02-data-model.md](../02-data-model.md), D16).
수집 예산이 남을 때만 가장 낮은 우선순위로 가져오며, 아이템 약 650개라 하루 약 650회로, 하루 예산(14만 4천 회)의 1% 미만이다.

## 불변식

- 다음 수집 예정 시각은 다음 원본 갱신 예상 시각이다. 추정이 불안정하면 마지막 수집 시각 + 고정 주기다.
- 한 번의 실행에서 쓰는 호출 수는 남은 예산을 넘지 않는다.
- 연속 실패가 일정 횟수(예: 5회)를 넘으면 해당 대상은 잠시 수집을 멈추고, 상태 페이지(F12)에 표시한다.
- API 전체 장애로 서킷 브레이커가 열려 있는 동안에는 수집 단위의 실패 횟수를 올리지 않는다 ([03-operations.md](../03-operations.md), D20).

## 포트와 공개 API

collector는 의존 방향의 가장 위에 있다. 다른 업무 모듈에 의존하지 않는다 (D24).

### `collector.api`: 아래쪽 모듈이 구현하는 인터페이스 (의존성 역전)

| 인터페이스 | 구현하는 곳 | 용도 |
|---|---|---|
| `MarketDataSink` | market | 수집 결과 저장 (D8) |
| `DemandSignalPort` | alert, user | 아이템별 활성 알림 수, 관심 수 |
| `PriceVolatilityPort` | market | 아이템별 최근 1시간 변동률 |

### `collector.api`: 공개 API (collector가 정의하고 구현)

| API | 쓰는 곳 | 용도 |
|---|---|---|
| `CollectionStatusQuery` | realtime | 서비스 상태 (정상 / 수집 지연 / 게임 점검). `freshness` 이벤트에 담는다 |

### 내부 포트 (collector 안에서만 사용)

| 포트 | 구현하는 곳 | 용도 |
|---|---|---|
| `LostArkMarketClient` | collector의 infrastructure | 로스트아크 API 호출. 응답 헤더의 남은 호출 수를 함께 돌려준다 |
| `LeadershipPort` | collector의 infrastructure | 이 인스턴스가 리더인지. M1~M3에서는 항상 참 |
