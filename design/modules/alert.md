# alert 모듈

> 핵심 도메인 · DDD 전술 설계를 충실하게 적용한다

alert가 답하는 질문은 두 가지다.

> 1. **"이 시세 갱신으로 누구에게 알림을 보내야 하나?"**
> 2. **"보내기로 한 알림이 제대로 도착했나?"**

두 질문은 책임이 다르므로 **애그리거트를 두 개로 나눈다** ([D9](../decisions.md#d9-알림을-pricealert와-notification-두-애그리거트로-나눈다)).

## 애그리거트 1: `PriceAlert`

사용자가 등록한 목표가 알림. "언제 보낼지"만 책임진다.

| 항목 | 내용 |
|---|---|
| 속성 | 사용자 ID, 아이템 ID, 조건(`TargetCondition`: 이상/이하 + 기준가), 받을 곳(DM, 웹) |
| 상태 | `ACTIVE`(감시 중), `PAUSED`(일시정지), `TRIGGERED`(조건 충족, 발송 완료) |

```
ACTIVE ──조건 충족──▶ TRIGGERED ──사용자가 다시 켬──▶ ACTIVE
  │  ▲
  │  └──────다시 켬──────┐
  └──일시정지──▶ PAUSED ─┘
```

### 불변식

- `ACTIVE`일 때만 `TRIGGERED`로 바뀔 수 있다.

이 전이를 DB 조건부 갱신으로 처리하고, 갱신된 행이 1개일 때만 발송한다.

```sql
UPDATE price_alert SET status = 'TRIGGERED'
WHERE id = ? AND status = 'ACTIVE'
```

시세 갱신 이벤트가 거의 동시에 두 번 처리되더라도 한쪽만 성공하므로 1회 발송이 보장된다 ([기획 4.2](../../planning/04-policies.md), D3).

## 애그리거트 2: `Notification`

실제로 보낸 알림 한 건. "제대로 보냈는지"만 책임진다.

| 항목 | 내용 |
|---|---|
| 속성 | 사용자 ID, 원인(목표가 알림 ID 또는 급변동 ID), 채널(DM/웹), 내용, 시도 횟수, 마지막 오류 |
| 상태 | `PENDING`(발송 대기) → `SENT`(성공) 또는 `FAILED`(사용자 쪽 원인으로 실패, 또는 일시 장애가 1시간 넘게 이어짐) |

- 이 기록이 그대로 **알림 내역(F10)**이 된다.
- DM은 이 상태로 재시도를 관리한다. 실패 원인을 둘로 나눈다 (D21).
  - **사용자 쪽 원인**(서버 이탈, DM 수신 거부): 즉시 `FAILED`로 바꾸고, user의 `DmStatusRecorder`로 DM 수신 상태를 알린다.
  - **일시 장애**(디스코드 5xx, 타임아웃, 429): 시도 횟수만 기록하고 재시도한다. 알림 생성 후 1시간이 지나면 `FAILED`로 바꾼다.
- 웹 토스트는 접속 중일 때만 한 번 보내고, 실패해도 재시도하지 않는다.

## 목표가 알림 처리 흐름

예시: 파괴석 시세가 139G로 갱신됨

```
1. PriceUpdated(파괴석, 139G) 수신
2. 조건 매칭      → 파괴석의 ACTIVE 알림 중 (이하 & 기준가 ≥ 139) 또는 (이상 & 기준가 ≤ 139)
                    DB 인덱스(아이템, 상태, 방향, 기준가)로 조회
3. 상태 전이      → 각 PriceAlert를 ACTIVE → TRIGGERED (조건부 갱신, 성공한 것만 다음 단계로)
4. 발송 기록 생성  → 받을 곳마다 Notification(PENDING) 생성
5. 발송           → 발송 워커가 PENDING을 가져가서 발송 (DM 성공 시 SENT, 실패 시 재시도 대기)
                    웹은 접속 중이면 realtime으로 토스트 전송
```

- **3번과 4번은 같은 트랜잭션**으로 묶는다. 상태는 바뀌었는데 발송 기록이 없는 상황을 막기 위해서다.
- **5번은 별도의 발송 워커가 트랜잭션 밖**에서 한다. 외부 API 호출을 트랜잭션 안에 넣지 않기 위해서다. 워커의 선점, 재시도, 전달 보장(최소 1번)은 [01-data-flow.md](../01-data-flow.md)와 D14를 따른다.
- 조건 매칭은 DB 인덱스 조회로 시작한다. 부하 테스트에서 병목이 확인되면 메모리 인덱스로 개선하는 것을 후속 개선 후보로 둔다.

## 급변동 판정: `SurgeDetector` (도메인 서비스, F11)

`PriceUpdated`를 받을 때 다음을 모두 만족하면 급변동 구독자 전원에게 `Notification`을 만든다 ([기획 4.3](../../planning/04-policies.md)).

- 1시간 변동률 ±10% 이상
- 거래량이 기준 이상
- 같은 아이템의 급변동 알림이 최근 1시간 안에 없음 (쿨다운)

## 사용자당 활성 알림 20개 제한

여러 `PriceAlert`에 걸친 규칙이라 애그리거트 하나로는 지킬 수 없다. 애플리케이션 서비스에서 등록 전에 개수를 확인한다.

같은 사용자가 거의 동시에 두 번 등록하면 21개가 될 수 있다. MVP에서는 이를 허용한다 ([D10](../decisions.md#d10-활성-알림-20개-제한의-동시-등록-경합은-mvp에서-허용한다)).

## 포트와 공개 API

alert는 collector, market, user에 의존한다 (D24).

### `alert.api`: 아래쪽 모듈이 구현하는 인터페이스 (의존성 역전)

| 인터페이스 | 구현하는 곳 | 용도 |
|---|---|---|
| `NotificationSender` | alert의 infrastructure(디스코드 DM), realtime(웹) | 채널별 발송 |

### alert가 쓰는 위쪽 모듈의 공개 API와 이벤트

| 대상 | 정의한 곳 | 용도 |
|---|---|---|
| `PriceUpdated` 이벤트 | `market.api` | 조건 매칭, 급변동 판정 |
| `UserQuery` | `user.api` | 알림 받을 사용자 정보, 급변동 구독자 목록 |
| `DmStatusRecorder` | `user.api` | DM 발송 결과 반영 |

### alert가 구현하는 위쪽 모듈의 인터페이스

| 인터페이스 | 정의한 곳 | 제공하는 것 |
|---|---|---|
| `DemandSignalPort` | `collector.api` | 아이템별 활성 알림 수 |
| `UserDeletionHook` | `user.api` | 탈퇴한 사용자의 `price_alert`, `notification` 삭제 (D19) |
