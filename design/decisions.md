# 기술 결정 기록

> 결정마다 **포기한 대안과 그 이유를 비워두지 않는다.** 나중에 결정을 다시 볼 때 "왜 그때 이걸 안 했지"에 답할 수 있어야 한다.

## D1. 백엔드를 모듈러 모놀리스 하나로 배포한다

- **날짜**: 2026-10-07
- **결정**: 애플리케이션 1개로 배포한다. M4 이후 인스턴스를 늘리고 리더 선출로 리더 1개만 수집한다.
- **이유**
  - 수집은 API 키 하나의 분당 100회를 나눠 쓰므로 반드시 1개만 돌아야 하고, API 서버는 여러 개로 늘릴 수 있어야 한다. 이 차이는 리더 선출만으로 해결된다.
  - 이 서비스의 핵심 지표는 데이터 신선도다. 수집 공백을 없애는 데는 리더 선출이 더 직접적이다.
- **포기한 대안**
  - **수집기 분리 + 수집기 1개 고정**: API 재배포와 부하로부터 수집을 보호하지만, 수집기 자체가 죽거나 재배포될 때 공백이 생긴다. 공백까지 없애려면 결국 수집기를 2개 띄우고 리더 선출을 해야 해서, 리더 선출의 대안이 아니라 그 위에 격리를 더하는 선택이다. 실사용자가 없어 격리 효과를 체감하기 어렵고, 저장소와 배포 파이프라인이 늘어난다.
  - **처음부터 마이크로서비스**: 3~4개월 1인 프로젝트에 과하다.
- **다시 검토할 조건**: 부하 테스트에서 API 서버 부하(SSE 연결 폭증, 메모리 부족)가 수집에 영향을 준다는 결과가 나오면 수집기 분리를 검토한다.

## D2. 주 DB로 PostgreSQL을 쓴다

- **날짜**: 2026-10-07
- **결정**: PostgreSQL 하나에 시세와 일반 데이터(사용자, 알림, 관심 아이템)를 모두 둔다. 시세는 날짜별로 파티셔닝하고, 분 단위 원본은 일정 기간만 보관한 뒤 롤업한다.
- **이유**
  - 대략 계산하면 시세가 하루 약 50만 행, 한 달 약 1,500만 행 쌓인다. 오래된 데이터를 파티션 단위로 지우고 롤업하는 구조가 처음부터 필요하다.
  - 날짜 기준 파티셔닝이 편하고, 나중에 TimescaleDB 확장과 비교해 볼 수 있다.
- **포기한 대안**
  - **MySQL**: `ticketing`에서 써봐서 익숙하지만, 파티셔닝 제약이 많고(파티션 키가 모든 유니크 키에 포함돼야 함) 시계열 확장 생태계가 약하다.
  - **RDB + 시계열 전용 DB(InfluxDB 등)**: 성능은 가장 좋지만 운영할 DB가 늘어나고, 이 데이터 규모에는 과하다.

## D3. Redis는 캐시, Pub/Sub, 세션에만 쓴다

- **날짜**: 2026-10-07
- **결정**: 최신 시세 캐시, 인스턴스 간 실시간 전달, 세션 공유에만 쓴다. 호출 제한 관리와 알림 중복 방지에는 쓰지 않는다. 리더 선출은 배포 환경 확정 후 결정한다.
- **이유**
  - 인스턴스 간 실시간 전달은 시세가 갱신될 때마다 발생하는 고빈도 메시지라 DB보다 Redis Pub/Sub이 맞다.
  - 수집은 리더 1개만 하므로 분산 카운터가 필요 없다. 메모리 카운터와 API 응답 헤더(남은 횟수)로 충분하다.
  - 알림 상태의 원본은 DB이므로 중복 방지도 DB의 조건부 갱신으로 하는 것이 정확하다.
- **포기한 대안**
  - **Redis 없이 PostgreSQL만 사용**(`LISTEN/NOTIFY`, 메모리 캐시, DB 세션): 구성 요소는 가장 적지만 고빈도 실시간 전달을 DB에 의존하게 된다.
  - **가능한 역할을 모두 Redis에 맡김**: 필요 없는 곳에도 Redis를 써서 원본 데이터가 두 곳으로 나뉜다.

## D4. 브라우저 실시간 전달은 SSE로 한다

- **날짜**: 2026-10-07
- **결정**: 시세 갱신, 랭킹 갱신, 알림 토스트를 SSE로 보낸다. 알림 등록 같은 요청은 REST API로 처리한다.
- **이유**
  - 실시간 데이터가 모두 서버 → 브라우저 한 방향이다.
  - 브라우저 `EventSource`가 자동 재연결을 지원해서 기획 4.6 정책을 대부분 기본 기능으로 충족한다.
  - 일반 HTTP라 프록시와 Ingress 설정이 단순하다.
- **포기한 대안**
  - **WebSocket + STOMP**: 주제별 구독이 편하지만 양방향 프로토콜이 필요 없는 요구사항이다.
- **감수한 점**: 페이지를 옮길 때마다 다시 연결해야 한다. 화면이 6개뿐이라 문제가 되지 않는다.

## D5. 이벤트는 받는 쪽이 여럿일 때만 쓰고, 나머지는 조회한다

- **날짜**: 2026-10-07
- **결정**
  - 시세 갱신(market → alert, realtime)만 Spring 이벤트로 메모리 안에서 전달한다.
  - 나머지 모듈 간 통신은 **호출하는 쪽이 정의한 인터페이스**로 조회한다. → **D24에서 보완**: 인터페이스를 누가 정의할지는 모듈 의존 방향에 따라 정한다.
  - DM 발송의 신뢰성은 alert 모듈의 DB 상태 전이로 보장한다.
- **이유**
  - 시세 갱신 이벤트는 놓쳐도 다음 갱신이 최신 상태를 다시 전달한다. 저장과 재시도를 붙이는 것은 낭비다.
  - 관심 수, 활성 알림 수를 이벤트로 collector에 전달하면, 이벤트 하나가 유실될 때 숫자가 영구히 어긋난다. 등급은 주기적으로 재계산하므로 그때 조회하면 항상 정확하다.
- **포기한 대안**
  - **관심 수·알림 수를 이벤트로 전달**: 유실 시 복구되지 않아 정기 보정 작업이 따로 필요하고, 같은 데이터를 두 곳에 복제하게 된다.
  - **Spring Modulith 이벤트(Event Publication Registry)**: 모든 이벤트를 DB에 기록하고 재시도하지만, 하루 수십만 건의 시세 이벤트 기록이 시세 저장과 비슷한 양의 쓰기를 추가로 만든다.
  - **메시지 브로커(Kafka, Redis Stream)**: 모놀리스 안의 통신에는 과하다.

## D6. DDD로 설계하고, 모듈 경계는 ArchUnit으로 검사한다

- **날짜**: 2026-10-07
- **결정**
  - 모듈을 바운디드 컨텍스트로 나눈다(전략 설계).
  - 애그리거트, 값 객체 같은 전술 설계는 도메인 규칙이 있는 alert와 collector에 집중하고, market과 user는 계층 구조 정도로 가볍게 간다.
  - 경계는 ArchUnit으로 핵심 규칙 몇 개만 테스트한다.
- **이유**
  - 도메인 규칙이 있는 곳(알림 상태 전이, 수집 등급과 예산)과 없는 곳(시세 저장·조회)이 뚜렷하게 나뉜다.
  - DDD는 설계 방법이고 Modulith는 경계 검사 도구라서 둘은 대체 관계가 아니다. 검사 도구는 가벼운 쪽을 고른다.
  - 모놀리스 안의 모듈은 패키지일 뿐이라, 다른 모듈 내부를 import해도 컴파일러가 막지 않는다. 혼자 개발하고 AI의 도움을 받으므로 경계를 넘는 코드가 모르는 사이에 생기기 쉽다. ArchUnit은 규칙 몇 개로 이를 테스트에서 잡는다. (2026-10-08 재확인 후 유지)
- **포기한 대안**
  - **Spring Modulith**: 규칙을 자동으로 검사하지만 Modulith의 패키지 관례를 따라야 한다. 이 프로젝트에서는 이벤트 기능도 쓰지 않으므로 얻는 것이 적다.
  - **Gradle 멀티모듈**: 컴파일 단계에서 막아 가장 강하지만 빌드 구성이 복잡해진다.
  - **관례로만 지킴**: 혼자 하면 조금씩 무너지기 쉽다.

## D7. 프론트엔드는 Vite + React SPA로 만든다

- **날짜**: 2026-10-07
- **결정**: Vite, React, TypeScript, shadcn/ui, TanStack Query, lightweight-charts. 백엔드 OpenAPI 문서에서 TypeScript 타입과 API 클라이언트를 자동 생성한다.
- **이유**
  - 프론트엔드는 코드를 거의 보지 않고 AI로 작성할 예정이다. 구조가 단순해야 AI가 만든 코드가 덜 꼬인다.
  - 검색 노출(SEO)은 비목표라서 서버 렌더링이 필요 없다. 빌드 결과가 정적 파일이라 배포도 단순하다.
  - API 타입을 자동 생성하면 AI가 응답 형식을 추측해서 만드는 일이 사라진다. API가 바뀌면 타입을 다시 생성하고, 깨진 곳을 AI에게 고치게 한다.
- **포기한 대안**
  - **Next.js**: 서버 렌더링과 SEO가 장점이지만 이 프로젝트에는 필요 없다. Node 서버가 하나 더 필요하고, 서버·클라이언트 컴포넌트가 섞여서 코드를 보지 않으면 원인을 찾기 어려운 버그가 생기기 쉽다.

## D8. collector → market은 인터페이스 호출로 한다

- **날짜**: 2026-10-07
- **결정**: collector가 `MarketDataSink` 인터페이스를 정의하고 market이 구현한다. collector는 수집 결과를 이 인터페이스로 저장한다. 저장이 끝나면 market이 `PriceUpdated` 이벤트를 발행한다.
- **이유**
  - 받는 쪽이 market 하나뿐이다 (D5 규칙).
  - collector가 저장 성공 여부를 알아야 다음 수집 예정 시각을 정하고, 실패하면 연속 실패 횟수를 올려 다시 시도할 수 있다.
- **포기한 대안**
  - **이벤트로 전달**: collector가 발행만 하고 끝나서 저장 실패를 모른다. 실패를 알리려면 market이 "저장 실패" 이벤트를 다시 보내야 해서 흐름이 오히려 복잡해진다.

## D9. 알림을 PriceAlert와 Notification 두 애그리거트로 나눈다

- **날짜**: 2026-10-07
- **결정**: 사용자가 등록한 목표가 알림(`PriceAlert`, "언제 보낼지")과 실제로 보낸 알림 한 건(`Notification`, "제대로 보냈는지")을 분리한다.
- **이유**
  - 발송 정보(재시도 횟수, 마지막 오류)가 알림 조건과 섞이지 않는다.
  - 급변동 알림(F11)은 사용자가 등록한 알림이 아니지만, `Notification`만 만들면 발송·재시도·내역 로직을 그대로 재사용할 수 있다.
  - `Notification` 기록이 그대로 알림 내역(F10)이 된다.
- **포기한 대안**
  - **하나의 애그리거트로 합침**: 테이블은 줄지만 `PriceAlert`에 발송 상태가 섞이고, 급변동 알림을 같은 구조에 넣기 어색하다.

## D10. 활성 알림 20개 제한의 동시 등록 경합은 MVP에서 허용한다

- **날짜**: 2026-10-07
- **결정**: 등록 전에 애플리케이션 서비스에서 개수만 확인하고, 동시 등록으로 21개가 되는 경우는 막지 않는다.
- **이유**
  - 사용자 한 명이 동시에 두 번 등록할 일은 드물고, 21개가 되어도 피해가 거의 없다.
- **포기한 대안**
  - **사용자 행 잠금(`SELECT ... FOR UPDATE`) 후 개수 확인**: 정확하지만 드문 경우를 위해 모든 등록에 잠금 비용을 낸다.
  - **사용자 테이블에 활성 알림 수 컬럼을 두고 조건부 증가**: 정확하지만 개수를 두 곳에서 관리하게 된다.
- **다시 검토할 조건**: 제한을 넘는 것이 실제 문제(예: 수집 등급 왜곡, 남용)로 이어지면 위 대안 중 하나를 적용한다.

## D11. 가격이 바뀐 아이템만 PriceUpdated를 발행한다

- **날짜**: 2026-10-07
- **결정**: market은 저장한 시세의 가격이 직전과 다를 때만 `PriceUpdated`를 발행한다. 단, `LatestPrice`의 갱신 시각은 가격이 같아도 항상 갱신한다.
- **이유**
  - 같은 가격이 다시 수집되면 alert의 조건 매칭 결과도, 화면에 보일 가격도 바뀌지 않는다. 이벤트 양이 크게 준다.
  - 갱신 시각을 항상 갱신해야 화면의 "마지막 갱신: N초 전"(F2)과 신선도 지표가 정확하다.
- **포기한 대안**
  - **수집할 때마다 발행**: 받는 쪽이 같은 일을 반복한다.
- **감수한 점**: 가격이 바뀌지 않으면 화면의 "마지막 갱신" 표시가 `price` 이벤트로는 갱신되지 않는다. → **D15의 10초 주기 `freshness` 이벤트로 해결했다.** (처음 검토한 "프론트엔드가 마지막 수신 시각부터 직접 센다"는 방법은, 가격이 안정적인 아이템을 지연된 것처럼 보이게 해서 버렸다.)

## D12. 급등락 랭킹은 30초마다 주기적으로 계산한다

- **날짜**: 2026-10-07
- **결정**: 시세가 갱신될 때마다가 아니라 30초마다 랭킹을 계산하고, 결과가 바뀌었을 때만 `RankingUpdated`를 발행한다.
- **이유**
  - 갱신마다 계산하면 1분에 수백 번 정렬하게 된다. 사용자 입장에서는 30초 간격도 충분히 실시간이다.
- **포기한 대안**
  - **갱신마다 계산**: 정확하지만 계산과 이벤트가 불필요하게 많아진다.

## D13. PriceUpdated는 모듈별 비동기 스레드 풀에서 처리하고, 대기열이 차면 버린다

- **날짜**: 2026-10-07
- **결정**
  - `PriceUpdated`는 저장 트랜잭션 커밋 후에 전달한다.
  - alert와 realtime은 각자 별도의 스레드 풀에서 비동기로 처리한다.
  - 대기열 크기를 제한하고, 가득 차면 새 이벤트를 버린다. 버린 개수는 지표로 남긴다.
- **이유**
  - 신선도가 핵심 지표이므로, 알림 처리가 느리다는 이유로 수집이 늦어지면 안 된다.
  - `PriceUpdated`는 놓쳐도 다음 갱신이 최신 상태를 다시 전달한다 (D5).
  - 스레드 풀을 나누면 SSE 전송 지연이 알림 처리에 번지지 않는다.
- **포기한 대안**
  - **수집 스레드에서 동기 처리**: 단순하지만 alert의 DB 조회와 상태 전이 시간만큼 수집이 느려진다.
  - **대기열 무제한**: 버리는 이벤트는 없지만, 처리가 계속 밀리면 메모리가 계속 늘고 오래된 시세를 뒤늦게 처리하게 된다.
- **감수한 점**: 이벤트를 버린 사이에 가격이 기준가를 잠깐 넘었다가 돌아오면 그 알림은 발송되지 않는다. 알림이 걸린 아이템은 HOT 등급이라 1분마다 다시 수집되고, 대기열이 차는 상황 자체가 드물어야 정상이다. 버린 이벤트 수를 지표로 감시해서 대응한다.

## D14. 알림 발송은 워커가 처리하고, 최소 1번 발송을 보장한다

- **날짜**: 2026-10-08
- **결정**
  - alert는 `Notification(PENDING)`을 DB에 기록하는 데서 끝나고, 실제 발송은 몇 초마다 도는 발송 워커가 한다 (아웃박스 패턴).
  - 워커는 `SELECT ... FOR UPDATE SKIP LOCKED`로 대상을 선점하고 선점 만료 시각을 기록한 뒤, 트랜잭션 밖에서 발송한다.
  - 전달 보장은 **최소 1번**이다.
- **이유**
  - 발송 지연 목표가 1분이라 워커 주기(몇 초) 지연은 문제가 되지 않는다.
  - 발송 경로가 하나라서 재시도, 재시작 후 복구, 디스코드 호출 제한 조절을 한 곳에서 처리한다.
  - `SKIP LOCKED`로 여러 인스턴스의 워커가 리더 선출 없이 일을 나눠 처리한다.
  - 목표가 알림은 "쌀 때 사라"는 신호라서, 같은 DM을 2번 받는 것보다 못 받는 쪽이 훨씬 나쁘다.
- **포기한 대안**
  - **커밋 직후 바로 발송 + 재시도 워커**: 지연은 가장 짧지만 발송 경로가 2개라 재시도와 호출 제한 처리가 두 곳에 나뉜다.
  - **최대 1번(누락 가능)**: 중복은 없지만, 발송 전에 서버가 죽으면 사용자가 DM을 받지 못한다.
- **감수한 점**: 디스코드 DM API에 멱등 키가 없어서, 발송 성공과 SENT 기록 사이에 워커가 죽으면 같은 DM이 2번 간다. 이 구간을 최소화하고, 기획 문서의 표현을 "정상 운영 중 중복 0건"으로 고쳤다.

## D15. "마지막 갱신" 시각은 10초 주기 freshness 이벤트로 전달한다

- **날짜**: 2026-10-08
- **결정**: realtime이 10초마다 연결된 브라우저에 구독한 아이템별 마지막 갱신 시각과 서비스 상태를 담은 `freshness` 이벤트를 보낸다. 값은 Redis의 `LatestPrice`에서 읽는다.
- **이유**
  - D11 때문에 가격이 같으면 `price` 이벤트가 없다. 프론트엔드가 마지막 수신 시각부터 세면, 실제로는 1분 전에 갱신된 아이템이 "10분 전, 갱신 지연"으로 보인다.
  - 수집 이벤트와 분리돼 있어서 D11의 장점(이벤트 양 감소)을 유지한다.
  - SSE는 어차피 연결 유지 신호가 필요하다. `freshness`가 그 역할을 겸한다.
  - 서비스 상태(수집 지연, 게임 점검) 배너도 같은 이벤트로 띄울 수 있다.
- **포기한 대안**
  - **가격이 같아도 수집할 때마다 갱신 시각 이벤트 발행**: 즉시 반영되지만 D11에서 줄인 이벤트 양이 다시 늘어난다.
  - **프론트엔드가 마지막 수신 시각부터 직접 셈**: 가격이 안정적인 아이템을 지연된 것처럼 보이게 한다.
- **감수한 점**: 갱신 시각이 화면에 최대 10초 늦게 반영된다. 표시가 "N초 전" 단위라 충분하다.

## D16. 시세 원본은 3일만 보관하고, 일별 값은 영구 보관한다

  - **TimescaleDB 연속 집계**: 롤업을 자동화하지만 확장 설치가 필요하다. 로드맵의 시계열 최적화 단계에서 직접 구현한 방식과 비교한다.

## D18. 모듈은 자기 테이블만 가지고, 모듈을 넘는 외래 키는 두지 않는다

- **날짜**: 2026-10-08
- **결정**: 다른 모듈의 테이블은 읽거나 JOIN하지 않고 포트로 묻는다. 모듈을 넘는 참조는 ID 값으로만 하고 FK를 두지 않는다. 모듈 안에서는 FK를 둔다.
- **이유**
  - 테이블 수준에서 모듈이 엉키면 코드 수준의 경계(D6)가 의미를 잃는다.
  - 나중에 모듈을 떼어낼 때(D1의 재검토 조건) DB도 함께 나눌 수 있다.
- **포기한 대안**
  - **모듈을 넘는 FK와 JOIN 허용**: 참조 무결성을 DB가 보장하고 조회가 편하지만, 모듈이 테이블 구조에 서로 묶인다.
- **감수한 점**: 모듈을 넘는 참조 무결성을 DB가 보장하지 않는다. 사용자 삭제처럼 정합성이 중요한 경우는 D19처럼 포트로 명시적으로 처리한다. ArchUnit은 테이블 접근을 검사하지 못하므로 코드 리뷰로 지킨다.

## D19. 회원 탈퇴 시 다른 모듈의 데이터는 user가 정의한 포트로 한 트랜잭션에서 삭제한다

## D20. 외부 API 호출에 Resilience4j 서킷 브레이커를 둔다

- **날짜**: 2026-10-08
- **결정**: 로스트아크 API와 디스코드 API 호출에 서킷 브레이커를 둔다. 로스트아크 API 회로가 열려 있는 동안에는 수집 단위의 실패 횟수를 올리지 않고, 서비스 상태를 "수집 지연"(구분 가능하면 "게임 점검")으로 표시한다.
- **이유**
  - 전체 장애 중에 계속 호출하면 호출 예산을 낭비하고, 모든 수집 단위가 하나씩 "수집 중단"이 되어 장애가 끝난 뒤에도 회복이 늦다.
  - 회로 상태가 Micrometer 지표로 바로 나가서 상태 페이지와 연결된다.
- **포기한 대안**
  - **직접 구현**: 동작은 단순하지만 상태 전이, 시험 호출, 지표 연동을 다시 만드는 일이다.
  - **서킷 브레이커 없이 수집 단위별 실패 횟수만 사용**: 개별 장애와 전체 장애를 구분하지 못한다.

## D21. DM 실패는 사용자 쪽 원인과 일시 장애로 나눠 처리한다

- **날짜**: 2026-10-08
- **결정**
  - 사용자 쪽 원인(서버 이탈, DM 수신 거부)이면 즉시 `FAILED`로 바꾸고 user에 DM 수신 상태를 알린다.
  - 일시 장애(5xx, 타임아웃, 429)면 간격을 늘려가며 재시도하고, 알림 생성 후 1시간이 지나면 `FAILED`로 바꾼다.
  - 기획 4.2의 "최대 3회 재시도"를 이 정책으로 바꾼다.
- **이유**
  - "3회 실패하면 FAILED"로 하면, 디스코드가 20분 동안 장애일 때 재시도가 모두 장애 중에 소진되어 복구 후에도 알림이 가지 않는다.
  - 사용자 쪽 원인은 재시도해도 소용없으므로 빨리 알려 웹 배너로 안내하는 편이 낫다.
  - 목표가 알림은 시간이 지나면 의미가 없어지므로, 제한을 횟수가 아니라 시간으로 둔다.
- **포기한 대안**
  - **횟수 제한 (3회)**: 단순하지만 장애 기간과 상관없이 재시도가 소진된다.
  - **무제한 재시도**: 몇 시간 뒤에 의미 없는 알림이 간다.

## D23. 수집 스케줄러 비교 실험은 로스트아크 API 시뮬레이터에서 한다

  - **실제 API로만 측정**: 실제 수치라 설득력은 있지만 비교 조건을 통제할 수 없다.

## D24. 모듈 의존 방향을 고정하고, 다른 모듈은 api 패키지만 참조한다

- **날짜**: 2026-10-08
- **배경**: 설계 전체를 자체 검토하다가, D5의 "인터페이스는 호출하는 쪽이 정의한다"를 모든 경우에 적용한 탓에 문제가 생긴 것을 발견했다.
  - alert가 `UserDirectory`를 정의하고 user가 구현, user가 `UserDeletionHook`을 정의하고 alert가 구현 → **alert ↔ user 순환 의존**
  - realtime이 market의 Redis 키(`price:latest`)를 직접 읽음 → D18 위반. 그렇다고 realtime이 인터페이스를 정의하면 market이 realtime에 의존하게 된다.
  - 포트를 `domain` 패키지에 두면, 구현하는 모듈이 다른 모듈의 `domain`을 참조하게 되어 ArchUnit 규칙과 충돌한다.
- **결정**
  1. 모듈 의존 방향을 고정한다: collector ← market, user ← alert ← realtime (그림은 [00-architecture.md](00-architecture.md)). 순환은 금지한다. user는 업무 모듈에 의존하지 않는다.
  2. 아래쪽이 위쪽을 호출하면 위쪽이 공개 API를 정의하고 구현한다. 위쪽이 아래쪽을 호출하면 위쪽이 인터페이스를 정의하고 아래쪽이 구현한다(의존성 역전). 어느 경우든 의존은 아래쪽 → 위쪽이다.
  3. 다른 모듈에 보여줄 것(공개 API, 의존성 역전용 인터페이스, 이벤트)은 `<모듈>.api`에 두고, 다른 모듈은 `api`만 참조한다.
- **바뀐 것**
  - `UserDirectory`(alert 정의, user 구현)를 없애고 `user.api.UserQuery`, `user.api.DmStatusRecorder`(user 정의, user 구현)로 바꿨다.
  - realtime은 Redis를 직접 읽지 않고 `market.api.LatestPriceQuery`, `collector.api.CollectionStatusQuery`로 조회한다.
  - ArchUnit 규칙을 "다른 모듈은 `api`만 참조", "의존 방향 그림을 따름", "순환 금지"로 바꿨다.
- **이유**
  - 의존성 역전은 위쪽 모듈이 아래쪽 모듈을 호출해야 할 때 방향을 지키기 위한 도구다. 방향을 먼저 정하지 않고 모든 호출에 적용하면 오히려 순환이 생긴다.
  - 순환이 있으면 한쪽만 떼어낼 수 없다 (D1의 재검토 조건).
- **포기한 대안**
  - **D5 규칙 그대로 두고 순환 허용**: 지금은 동작하지만 모듈 경계가 의미를 잃는다.
  - **alert와 user를 하나의 모듈로 합침**: 순환은 사라지지만 지원 모듈(user)과 핵심 도메인(alert)이 섞인다.
