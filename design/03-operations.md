# 03. 장애 처리와 관측성

## 장애 시나리오

| 고장 나는 것 | 서비스 동작 | 사용자에게 보이는 것 |
|---|---|---|
| 로스트아크 API 일시 오류 (5xx, 타임아웃) | 해당 수집 단위의 실패 횟수 +1, 짧게 미뤄 재시도 ([collector](modules/collector.md)) | 해당 아이템만 🟡 갱신 지연 |
| 로스트아크 API 전체 장애 또는 게임 점검 | 서킷 브레이커가 호출을 멈춤 (아래) | 🔴 상단 배너 (수집 지연 / 게임 점검) |
| API 호출 한도 초과 (429) | 응답 헤더의 초기화 시각까지 수집 중단. 정상이라면 일어나면 안 되므로 지표로 기록 | 짧은 갱신 지연 |
| 디스코드 장애 | 실패 원인을 구분해 재시도 (아래) | DM이 늦게 옴 |
| Redis 장애 | 시세 캐시는 DB에서 직접 읽는다. 세션이 사라져 로그인이 풀린다. M4 이후에는 인스턴스 간 실시간 전달이 끊긴다 | 다시 로그인 필요, 실시간 갱신이 늦어질 수 있음 |
| PostgreSQL 장애 | 서비스 전체 중단. 수집은 저장 실패로 처리되고 DB가 돌아오면 재개한다 | 서비스 이용 불가 |
| 인스턴스 재시작 | SSE 연결이 끊기고 브라우저가 자동 재연결한다 (D4). 발송 중이던 알림은 선점 만료 후 다른 워커가 처리한다 (D14) | 잠깐 "재연결 중" 표시 |

## 로스트아크 API 전체 장애: 서킷 브레이커

[D20](decisions.md#d20-외부-api-호출에-resilience4j-서킷-브레이커를-둔다)

API가 통째로 죽었는데 계속 호출하면 호출 예산만 낭비하고, 모든 수집 단위의 실패 횟수가 쌓여 하나씩 "수집 중단" 상태가 된다. 장애가 끝난 뒤에도 정상으로 돌아오는 데 시간이 걸린다.

```
닫힘(정상) ──최근 호출 실패율이 기준(예: 50%) 초과──▶ 열림(호출 중단)
   ▲                                                    │ 일정 시간 후
   └──────────시험 호출 성공────── 반열림(몇 번만 시험 호출) ◀─┘
```

- 회로가 열려 있는 동안에는 **수집 단위의 실패 횟수를 올리지 않는다.** 개별 단위의 문제가 아니라 전체 장애이기 때문이다.
- 회로가 열리면 `system:status`를 "수집 지연"으로 바꾼다. 게임 점검 응답을 구분할 수 있으면 "게임 점검"으로 표시한다 (점검 응답의 형태는 M0에서 확인).
- 구현은 Resilience4j를 쓴다. 회로 상태가 Micrometer 지표로 바로 나간다.

## 디스코드 DM 실패: 원인별 처리

[D21](decisions.md#d21-dm-실패는-사용자-쪽-원인과-일시-장애로-나눠-처리한다)

| 실패 원인 | 예시 | 처리 |
|---|---|---|
| 사용자 쪽 원인 (재시도해도 소용없음) | 서버를 나감, DM 수신 거부 | 즉시 `FAILED`. user에 DM 수신 상태를 알려 웹 배너를 띄운다 |
| 일시 장애 (기다리면 해결됨) | 디스코드 5xx, 타임아웃, 429 | 간격을 늘려가며 재시도. 알림 생성 후 **1시간이 지나면** `FAILED` |

- 사용자 쪽 원인은 디스코드가 오류 코드로 알려준다.
- 일시 장애의 제한을 횟수가 아니라 시간으로 두는 이유: 목표가 알림은 시간이 지나면 의미가 없어진다. 1시간 뒤에 "파괴석이 139G가 됐어요"를 받아도 이미 가격이 바뀌었을 가능성이 크다.
- 디스코드 호출에도 서킷 브레이커를 둔다. 장애 중에 워커가 계속 호출하지 않게 한다.
- 디스코드가 429를 주면 응답에 담긴 대기 시간만큼 기다린다 (D14).

## 관측성

지표는 Micrometer로 만든다. **무엇을 측정할지는 여기서 정하고, 수집·저장 도구 조합(예: Prometheus + Grafana + Loki)은 배포 환경과 함께 정한다.**

### 측정할 지표

포트폴리오의 성공 지표([기획 05](../planning/05-milestones.md))를 증명하는 지표가 핵심이다.

**수집**

| 지표 | 의미 | 연결되는 성공 지표 |
|---|---|---|
| 등급별 갱신 지연 (p50, p95) | 지금 시각 - 마지막 갱신 시각 | Hot 갱신 지연 1분 이내, M1 기준선 대비 개선 |
| 목표를 넘긴 수집 단위 수 | 지연 비율이 1을 넘은 대상 수 | |
| 분당 API 호출 수, 남은 한도 | 예산 사용량 | |
| API 한도 초과(429) 횟수 | 정상이면 0 | 한도 초과 0건 |
| 서킷 브레이커 상태 | 로스트아크, 디스코드 각각 | |

**이벤트 처리**

| 지표 | 의미 |
|---|---|
| 모듈별 대기열 길이, 버린 이벤트 수 | D13에서 감수한 위험을 감시 |

**알림**

| 지표 | 의미 | 연결되는 성공 지표 |
|---|---|---|
| 발송 지연 (p95) | 시세 수집 시각 → DM 발송 완료 시각 | 알림 발송 지연 p95 1분 이내 |
| `PENDING` 개수, 원인별 `FAILED` 수 | 발송이 밀리는지, 왜 실패하는지 | |
| 선점 만료 후 재처리 횟수 | 중복 발송이 생겼을 수 있는 건수 (D14) | 정상 운영 중 중복 0건 |

중복 발송은 직접 셀 수 없으므로 "선점 만료 후 재처리 횟수"를 대신 쓴다. 이 값이 0이면 중복이 없었다고 말할 수 있다.

**실시간**

| 지표 | 의미 | 연결되는 성공 지표 |
|---|---|---|
| 인스턴스별 SSE 연결 수, 전송 실패 수 | | 동시 접속 한계치 측정 (부하 테스트) |

HTTP 요청, JVM, DB 커넥션 풀 같은 기본 지표는 Spring Boot Actuator가 자동으로 만든다.

### 대시보드와 상태 페이지 (F12)

[D22](decisions.md#d22-상태-페이지는-grafana-공개-대시보드로-보여준다)

| 대상 | 내용 |
|---|---|
| 내부 운영 대시보드 | 모든 지표. 외부에 노출하지 않는다 |
| 공개 쇼케이스 대시보드 | 포트폴리오용 지표만 담은 대시보드 하나를 Grafana의 **공개 대시보드 기능**으로 읽기 전용 링크 공유 (등급별 갱신 지연, API 호출과 남은 한도, 알림 발송 지연, 중복 의심 건수, SSE 연결 수) |
| 서비스의 `/status` 화면 | 공개 대시보드를 화면 안에 넣어(임베드) 보여준다. 넣기 어려우면 링크로 연결한다 |
| 사용자용 상태 표시 | 상단 배너(수집 지연, 게임 점검)는 `freshness` 이벤트로 처리한다 (D15). Grafana와 상관없다 |

- **Grafana 자체(로그인 화면, 관리 기능)는 인터넷에 노출하지 않는다.** 공개 대시보드 링크만 외부에서 접근할 수 있게 한다.
- Grafana가 죽어도 서비스 이용에는 영향이 없다. 사용자가 보는 서비스 상태는 백엔드가 따로 처리한다.

### 운영 알람

지표가 기준을 넘으면 **운영자용 디스코드 채널**로 알람을 보낸다. 사용자 알림과는 별개다.

- HOT 갱신 지연 p95가 2분을 넘은 상태가 10분 지속
- 서킷 브레이커 열림
- 버린 이벤트 발생, `FAILED` 급증

### 로그

- JSON 형식의 구조화 로그로 남긴다.
- 요청마다 추적 ID를 붙인다.
- 로그를 모으는 도구는 배포 환경과 함께 정한다.
