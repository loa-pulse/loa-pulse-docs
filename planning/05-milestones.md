# 05. 마일스톤, 성공 지표, 리스크

## 전제

- 기간은 **15주(약 3.5개월)**, 주 10~15시간으로 총 150~220시간이다.
- 모든 마일스톤은 **"동작하는 상태로 배포"**로 끝난다. 중간에 멈춰도 그 시점까지의 결과물이 포트폴리오가 되도록 하기 위해서다.
- 마일스톤마다 **측정 기록**을 남긴다. 개선 전후 수치가 포트폴리오의 핵심 근거다.

## 마일스톤

| 단계 | 기간 | 목표 | 포함 기능 | 완료 기준 |
|---|---|---|---|---|
| M0. 사전 조사 | 1주 | API와 도메인 파악 | - | API 키 발급, 호출 1번에 몇 개 아이템이 오는지와 호출 제한 헤더 확인, 수집 대상 아이템 목록 확정, 신선도 목표 수치 확정, 용어집 검증 |
| M1. 시세 파이프라인 v1 | 3주 | 가장 단순한 형태로 처음부터 끝까지 동작 | F1, F2, F3 | 고정 주기 수집, 목록·상세·차트 화면, 홈서버 배포와 CI/CD, 로스트아크 API 시뮬레이터, **시뮬레이터에서 기준선(baseline) 갱신 지연 측정** |
| M2. 실시간 | 2주 | 새로고침 없는 시세 화면 | F4, F5 | 상세 화면 실시간 갱신, 급등락 랭킹 실시간 갱신 |
| M3. 계정과 알림 | 3주 | 메인 시나리오(S1) 완성 | F6, F8, F9 | 디스코드 로그인과 서버 자동 참여, 목표가 알림 등록·발송, DM 실패 대비책 |
| M4. 수집 스케줄러 고도화 | 3주 | **메인 기술 스토리** | F7 | Hot/Normal/Cold 등급제, 관심·알림 신호 반영, **M1 기준선 대비 개선 수치 확보** |
| M5. 운영과 쇼케이스 | 2주 | 증명 가능한 상태 만들기 | F12, F10, (F11) | 상태 페이지 공개, 부하 테스트 리포트 |
| M6. 정리 | 1주 | 포트폴리오 마감 | - | README, 기술 블로그, 데모 영상 |

### M4가 M3 뒤에 있는 이유

- 등급제는 관심 아이템과 알림 등록을 우선순위 신호로 쓰므로, 사용자 기능이 먼저 있어야 의미가 생긴다.
- M1의 단순한 수집기로 기준선을 먼저 측정해 둬야 개선 효과를 비교할 수 있다.

## 일정이 밀릴 때 버리는 순서

1. F11 급변동 알림
2. F10 알림 내역
3. F7 관심 아이템 (M4 등급제는 알림 신호만으로 진행)

**F12 상태 페이지는 끝까지 지킨다.** 면접관이 측정 결과를 직접 볼 수 있는 창구이기 때문이다.

## 성공 지표

### 1. 기능 완성도

- P0 기능이 전부 동작한다.
- 서비스가 상시 접속 가능한 상태로 배포돼 있다.

### 2. 측정으로 증명할 수치

목표치는 가안이며 M0 이후 확정한다.

| 지표 | 목표 (가안) |
|---|---|
| Hot 아이템 평균 갱신 지연 | 1분 이내. M1 기준선 대비 개선 폭을 제시 |
| API 호출 한도 초과 횟수 | 0건 |
| 목표가 알림 발송 지연 (p95) | 시세 갱신 후 1분 이내 |
| 알림 중복 발송 | 정상 운영 중 0건 (서버 장애 시의 중복은 설계상 허용) |
| 실시간 연결 동시 접속 | 부하 테스트로 한계치를 측정하고 기록 |

### 3. 포트폴리오 산출물

- README: 서비스 소개, 아키텍처, **개선 전후 수치**
- 트러블슈팅 기록 3건 이상 (문제 → 원인 분석 → 해결 → 결과 수치)
- 기술 블로그 2편 이상 (수집 스케줄러, 알림 시스템)
- 공개된 상태 페이지 URL

## 리스크

| 리스크 | 대응 |
|---|---|
| API 정책 변경 (호출 한도 축소, 엔드포인트 변경) | M0에서 약관과 공지를 확인하고, 수집 계층을 API 변경에 대비해 분리한다 |
| 도메인 이해 부족 (로아 미플레이) | 용어집을 작성하고, 인벤 등 커뮤니티의 시세 관련 글을 참고한다 |
| 일정 지연 | 위의 "버리는 순서"대로 범위를 줄이고, 마일스톤마다 배포 상태를 유지한다 |
| 실사용자가 없어 측정 데이터가 부족 | 부하 테스트와 시뮬레이션 사용자로 보완한다 (실사용자 확보는 비목표) |
